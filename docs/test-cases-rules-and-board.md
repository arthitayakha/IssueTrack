## 0. ก่อนเริ่มทดสอบ

### 0.1 บัญชีทดสอบ (รหัสผ่าน `123456` ทุกบัญชี)

| บทบาท | อีเมล | ใช้ทดสอบอะไร |
| --- | --- | --- |
| admin | `aom@gmail.com`<br />`admin@gmail.com` | สร้าง/แก้/ลบกฎ, ทุกเคสหลัก, ปลดล็อกการ์ด — **มี 2 คน ใช้ทดสอบ fan-out แจ้งเตือนข้ามแอดมินได้** |
| programmer | `programmer@gmail.com` (ตำแหน่ง Frontend)<br />`b@gmail.com` (ตำแหน่ง Backend) | ไม่มี `automation.*`; **มีตำแหน่ง → ใช้ permission ของตำแหน่งร่วมกับ role** (Frontend ให้เพิ่มหลายตัว, Backend ให้ `issue.delete`) |
| customer | `arthitaya@gmail.com` | ไม่มีตำแหน่ง — จำกัดสิทธิ์ตาม role จริง (**ไม่มี** `issue.delete` / `issue.all.update` / `time.actual.edit` / `automation.*`) |

> ⚠️ **สิทธิ์ effective = role ∪ ตำแหน่ง** — programmer ทั้งสองคนมีตำแหน่ง ดังนั้นบางเคสที่คิดว่า "ไม่มีสิทธิ์" อาจมีจริงมาจากตำแหน่ง เช่น `b@gmail.com` (Backend) **มี `issue.delete`** ลบการ์ดได้ทุกสถานะ ขณะที่ customer (`arthitaya`) ไม่มีเลย ลบไม่ได้แม้แต่ใน Backlog

### 0.2 ข้อมูลตั้งต้นที่ต้องเตรียมก่อนเริ่ม

- สถานะอย่างน้อย **4 คอลัมน์** (เช่น Backlog → กำลังดำเนินการ → รอตรวจสอบ → เสร็จสิ้น)
- **Position** 2 ตัวพร้อม user แล้ว: **Frontend** (`programmer@gmail.com`) และ **Backend** (`b@gmail.com`) — ใช้กับ action "มอบหมาย" และเป็นแหล่ง permission ของ programmer
- **Label** ≥ 2 ตัว · **Category** ≥ 2 ตัว · **Priority** ≥ 2 ระดับ
- ผู้ใช้แต่ละบัญชีรู้จัก "การ์ดทดสอบ" ของตัวเอง (สร้างใหม่ตอนเริ่มแต่ละ TS จะดีที่สุด)

### 0.3 กติกาสำคัญ 3 ข้อ (อ่านก่อนทุกครั้ง)

1. **ก่อนเริ่มแต่ละกลุ่ม TS: pause กฎอื่นทั้งหมด** ใน `/automation` และเหลือไว้เฉพาะกฎที่เคสนั้นใช้ — ไม่งั้นผลทดสอบปนกัน
2. **กฎ "บังคับลากการ์ดทีละคอลัมน์" ถูก seed มาเปิดอยู่แล้ว** (`issue.move_step_only`) — เคสที่ต้องลากอิสระให้ pause ก่อน แล้ว **resume คืนหลังจบเคสเสมอ**
3. **Skip reason เห็นแค่ใน log เซิร์ฟเวอร์** (ฝั่ง API) — UI ไม่แสดง เช่น `timer already running` / `no user to own the timer`

### 0.4 ข้อเท็จจริงของระบบที่นักทดสอบต้องรู้

| # | ความจริงของระบบ                                                                                                                                                           | ผลกระทบต่อการทดสอบ                                                                                              |
| - | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |

| 4 | `work_session.started` / `work_session.stopped` **จุดจาก UI ตรง ๆ ไม่ได้** (บอร์ดไม่มีปุ่มจับเวลา — นาฬิกาเดินเพราะ rule) | ทดสอบ 2 trigger นี้ผ่าน rule ตอนลาก หรือยิง API `POST /work-sessions/issue/:id/start` และ `/stop` |
| 5 | สร้างการ์ด **พร้อมหมวดหมู่** = ยิงทั้ง `issue.created` **และ** `issue.category_changed` (oldValue = null)                               | เคส category_changed มี 2 ทางจุดชนวน (สร้างการ์ด / แก้ใน detail)                                    |
| 6 | กฎ `move_step_only` **เมินเงื่อนไขของตัวเอง** (ตั้งอะไรก็เหมือนกัน)                                                                    | อย่าทดสอบความต่างของเงื่อนไขในกฎนี้                                                            |
| 7 | เงื่อนไขในกฎ 1 ใบ = **AND เท่านั้น** (ยังไม่มี OR ในระบบ)                                                                                      | เคสหลายเงื่อนไขต้อง "จริงพร้อมกันทุกข้อ"                                                     |
| 8 | หน้า `/automation` ทั้ง 4 หน้ากันด้วย `automation.update` (ไม่ใช่ `automation.view`)                                                                      | เคสสิทธิ์ต้องแยก "ดูได้แต่แก้ไม่ได้" ให้ชัด                                                |
| 9 | **สิทธิ์ effective = role ∪ ตำแหน่ง** — บัญชี programmer ทั้งสองคนมีตำแหน่ง (`Frontend`/`Backend`) ที่ให้ permission เพิ่ม เช่น `b@gmail.com` มี `issue.delete` จากตำแหน่ง Backend | ก่อนเขียน/รันเคสสิทธิ์ ให้เช็คตำแหน่งของบัญชีนั้นก่อน — อย่าเหมาว่า "programmer ไม่มีสิทธิ์ X" เสมอไป |
