## Commands / คำสั่ง

Run from the repo root. **ไทย:** รันจาก root ของ repo

```bash
npm install
npm run dev                            # turbo: web + api
npm run dev --workspace=@kanban/web    # frontend only
npm run dev --workspace=@kanban/api    # backend only
npm run lint
npm run typecheck
npm run build
npm test                                    # jest unit tests (apps/api) — no DB, no build
npm run test:e2e --workspace=@kanban/api    # 4 live suites — needs API on 3002 + local DB
npm run migration:run                       # no-op while nothing is pending
npm run migration:generate                  # needs a name/path argument
```

- `npm run test:e2e --workspace=@kanban/api` runs `apps/api/test/e2e/run-all.js` — suites `rules-api`, `engine-actions`, `run-history`, `notifications` against a live API + DB. They log in with seeded accounts, create and delete test data, and **suspend any rule already in the DB, restoring its `isActive` afterwards** (hand-made rules would otherwise move the test cards). Not part of `npm test`.

Raw SQL in `apps/api/migrations/*.sql` is applied by hand and is not tracked. Three extra TS files live in `apps/api/migrations/` and are **not wired into data-source**: `1794000000000-AddStatusTimerLockColumns` was applied by hand (columns exist), `1793000000000-DropUnusedIssueColumns` was **not** (`issues.assigned_at` still exists).

## Structure / โครงสร้าง

- `apps/web` — Next.js frontend. Path alias `@/*` → `src/*`. Imports `@kanban/shared` as raw TS. Uses `next-intl` for i18n (locales: `th` default, `en`).
- `apps/api` — NestJS. Implemented (controller + service): `auth`, `permissions`, `users`, `roles`, `positions`, `issues`, `issue-statuses`, `issue-priorities`, `categories`, `activity-logs`, `work-sessions`, `comments`, `attachments`, `labels`, `rules`, `notifications`. **No stubs left**, and **no `columns` module** (board columns are statuses — see Domain rules). `rules` = CRUD + `RulesEngineService` + `rule_runs` history; `notifications` = inbox/list/mark-read/archive. **There is NO `boards` module/table** — the app is single-board.
- `apps/web` also has `apps/web/src/app/[locale]/automation/**` (rule wizard + list + run history), `/notifications` (inbox) and a navbar bell polling `GET /notifications/count` (badge = bare number; the inbox ROWS load only when the bell opens).
- `packages/shared` — types/DTOs/permissions/rules registry consumed as raw TS (`main` → `src/index.ts`); **no build step**. Resolved via workspace symlink and root tsconfig path `@kanban/shared` → `packages/shared/src`.
- **ไทย:** `apps/web` ใช้ alias `@/*` → `src/*` และ import `@kanban/shared` เป็น TS ตรง ๆ; ใช้ `next-intl` (locale เริ่มต้น `th`)
- **ไทย:** `apps/api` implement ครบทุกโมดูลแล้ว (ไม่มี stub): `auth`, `permissions`, `users`, `roles`, `positions`, `issues`, `issue-statuses`, `issue-priorities`, `categories`, `activity-logs`, `work-sessions`, `comments`, `attachments`, `labels`, `rules`, `notifications` — **ไม่มีโมดูล `columns`** (คอลัมน์บอร์ด = สถานะ ดูกฎระบบ) และ **ไม่มีโมดูล/ตาราง `boards`** — แอปเป็นแบบบอร์ดเดียว. `rules` = CRUD + engine + ประวัติ `rule_runs`; `notifications` = รายการ/อ่านแล้ว/เก็บถาวร
- **ไทย:** ฝั่งเว็บมี `/automation/**` (wizard + รายการ + ประวัติการรัน), `/notifications` และกระดิ่งใน navbar ที่ poll `GET /notifications/count` (badge = ตัวเลขล้วน; **แถว**ของกล่องเข้าจะโหลดเฉพาะตอนกดเปิดกระดิ่ง)
- **ไทย:** `packages/shared` ถูกใช้เป็น TS ดิบ ไม่มี build step (รวม registry ของกฎ)

## Domain rules — single board / ข้อจำกัดระบบ — บอร์ดเดียว

- **One board only.** Do NOT add a `boards` table/entity/controller/service, a board list, a board selector, or board CRUD. The app is single-board.
- The sidebar "บอร์ด"/"Board" item links straight to `/boards` — that page **is** the board (no intermediate board list). The board loads with `fetchStatuses()` / `fetchIssues()` → `GET /issue-statuses` and `GET /issues`. **There is no `/columns` endpoint and no `columns` module.**
- **"Add column" = "add status".** `AddColumnInline` (`[locale]/boards/page.tsx`) collects a name + description and calls `createStatus()` → `POST /issue-statuses`; the board's columns *are* the statuses. A card's column is its `status_id`.
- The `board_columns` table still exists in the DB but **nothing writes to it** — legacy of migration `0025-merge-board-columns-into-issue-statuses.sql`. Do not build features on it.
- **Drift / legacy — do not reintroduce `board_id`:** migration `1791200000000-RemoveBoardsAndAddTimeTracking.ts` dropped `board_id`. The `Issue` entity no longer maps it (nor `column_id`), although the DB still carries a dead `issues.column_id` column. The old issue **list** page is gone — only `/issues/new` remains, and the list comes from `GET /issues`. Never point frontend code at `/issues/boards/...` (not in `IssuesController`).
- **ไทย:** มีบอร์ดเดียว — ห้ามเพิ่มตาราง `boards`, entity/controller/service ของบอร์ด, หน้ารวมบอร์ด, ตัวเลือกบอร์ด หรือ CRUD บอร์ด
- **ไทย:** ปุ่ม "บอร์ด" เข้า `/boards` ตรง ๆ หน้านั้นคือตัวบอร์ด; บอร์ดโหลดด้วย `fetchStatuses()` / `fetchIssues()` → `GET /issue-statuses` และ `GET /issues` — **ไม่มี endpoint `/columns` และไม่มีโมดูล `columns`**
- **ไทย:** "เพิ่มคอลัมน์" = "เพิ่มสถานะ" — `AddColumnInline` รับชื่อ + คำอธิบายแล้วเรียก `createStatus()` → `POST /issue-statuses`; คอลัมน์ของบอร์ดคือสถานะ ส่วนคอลัมน์ของการ์ดคือ `status_id`
- **ไทย:** ตาราง `board_columns` ยังอยู่ใน DB แต่**ไม่มีอะไรเขียนลงไปแล้ว** — เป็นของเก่าจาก migration `0025`; อย่านำไปสร้างฟีเจอร์ใหม่
- **ไทย:** อย่านำ `board_id` กลับมา — migration `1791200000000` ลบไปแล้ว entity `Issue` ไม่ map `board_id`/`column_id` อีก (แต่ DB ยังมีคอลัมน์ `issues.column_id` ที่ไม่ถูกใช้อยู่); หน้า list การ์ดถูกลบแล้วเหลือแค่ `/issues/new` และรายการมาจาก `GET /issues` — ห้ามชี้ไป `/issues/boards/...` ที่ไม่มีใน `IssuesController`

## Backend facts / ข้อเท็จจริงฝั่ง backend

- `main.ts`: global `ValidationPipe({ whitelist: true, transform: true })`, wide-open CORS, listens on `PORT` ?? 3002.
- `JwtAuthGuard` is registered **globally** via `APP_GUARD`; opt out per route with `@Public()`. Secret `JWT_SECRET` (default `"secret"`), expiry **7d**. No refresh-token flow.
- There is **no auto-seed on boot**. Accounts come from `apps/api/src/seed.ts` (`npm run seed`), which would create `admin@example.com` / `admin123` — that account does **not** exist in the local DB. The local DB has 4 users: `aom@gmail.com` (admin, id 1), `arthitaya@gmail.com` (id 2), `programmer@gmail.com` (id 13), `b@gmail.com`, all with password `123456`.
- `User.id` is an **integer** auto-increment PK (not UUID); password column is named `password` but maps to `passwordHash`. `RolePermission.id` **is** a uuid — PK types are mixed. `packages/shared` types say `id: string`; the API returns `String(user.id)`.
- DB env vars are `DB_HOST` / `DB_PORT` / `DB_USER` / `DB_PASSWORD` / `DB_NAME` (`apps/api/.env`); code defaults `localhost` / `5432` / `postgres` / `1234` / `trackdb`. `synchronize: false` always — schema changes need a migration (see Commands for which runner does what).
- **Automation permissions**: `automation.view` / `automation.update` (migration `0031-add-automation-permissions.sql`, granted to admin). `RulesController` is guarded by them; the 4 `/automation` pages gate on `automation.update`.
- **Move guard — "one column at a time"**: an active rule with action `issue.move_step_only` (trigger `issue.moved`, template `moved_any`) makes `IssuesService.move()` throw **400 before writing** on any non-adjacent jump (adjacency = index in `issue_statuses.position` order, i.e. the board's column order; cards with `statusId: null` and unreadable status lists pass — fail open). The one flag is `RulesEngineService.isStepOnlyMoveActive()`; its `case "issue.move_step_only":` in `runAction` must stay (the registry test demands a case for every supported action) and it returns *skipped* — the engine still runs after a real move. `GET /issues/move-policy` → `{ stepOnly }` is what the board uses to skip the drop preview (`Boards.invalidTransition` i18n key + a 400 fallback in `handleDragEnd`). Seeded **ON** by migration `1801000000000` ("บังคับลากการ์ดทีละคอลัมน์"); pause it in `/automation` for free dragging again. The action's own conditions are ignored on purpose (preview flag and server check must agree), and rule action `issue.move_status` writes directly so automation still jumps columns.
- **Status locks — "การ์ดในสถานะนี้ลากออกไม่ได้"**: an active rule with action `issue.lock` **that names statuses** (a `to_status` condition, e.g. template `moved_to`) freezes every card sitting in those statuses. It is **derived at read/move time** from `RulesEngineService.statusGates(...).locked` — cards already in the status lock the moment the rule is turned on, and pausing the rule frees them immediately — so that rule's `case "issue.lock":` in `runAction` writes **no per-card flag** (reason: "status lock is enforced at read time"); only a *condition-less* `issue.lock` rule still writes `issues.is_locked` on its trigger (per-card lock, e.g. "created → lock"). `IssuesService.move()` throws **409 Conflict before writing** when the card's status is locked or `is_locked` is set (board shows `Boards.lockedCard`; the drag handle is already disabled client-side via `issue.isLocked`, so 409 is the backstop for stale state — 409 not 400 so it is distinguishable from the step-only guard). **One-shot release**: `PUT /issues/:id/unlock` (perm `issue.all.update`) clears `is_locked` and sets `lock_exempted` (migration `1802000000000`); the next successful move consumes it (`lock_exempted: false` in the same write), so re-entering a locked status locks the card again. The board only offers the unlock affordance (card "..." menu + bottom-bar lock icon) while **at least one active `issue.unlock` rule exists** — `GET /issues/move-policy` → `{ stepOnly, unlockAvailable }`, fail-closed on lookup errors; without an unlock rule a locked status is sealed and admins release cards by pausing the lock rule. `toResponse()` sends `isLocked` = per-card flag OR status gate, minus a pending `lock_exempted`. The unlock **rule action** (`issue.unlock` fired by a trigger) does the same as the endpoint: `{ isLocked: false, lockExempted: true }`.
- **Notifications API — single inbox, no tabs, reading = deleting**: `GET /notifications` (returns `{ data, unreadCount }`, **no `tab` param** — every stored row is unread), `GET /notifications/count` (badge only → `{ count }`, one COUNT over the caller's rows — the navbar polls this every 30s instead of the rows; a module-level single-flight promise in `navbar.tsx` keeps StrictMode/remounts from doubling it), `DELETE /notifications/:id` (reading a row deletes it; another user's id matches nothing → `null`), `DELETE /notifications` (clears the whole inbox → `{ deleted: n }`) — each scoped to their owner. The inbox ROWS are fetched only when the bell opens (`status` idle→loading→ready|error in `notification-popover.tsx`: spinner on first open, `Notifications.retry` on failure; a sequence ref drops late responses so a stale page cannot clobber a newer one). Rows carry only `actor_id` + `title`/`context`/`link`/`type`: the display name is joined from `users` at read time. Migration `1804000000000` dropped `notifications.actor_name`/`message`/`is_read`/`is_archived`/`read_at` (pre-deleting rows that were already read) **and** `activity_logs.actor_name`/`actor_role` — so `GET /issues/:id/activity` and `GET /rules/activity` resolve names through an `actor → users → roles` join too. Rows are skipped for the actor and deduped across recipients; `notify()` never throws, so a notification failure cannot break the request that triggered it. **Who hears about what — the recipient policy lives in `NotificationsService`** (`notifyStatusChange()` / `notifyAssignmentChange()`), shared by manual drags (`IssuesService.move/assign`) and by the rules engine (`issue.move_status` / `issue.assign` / `issue.unassign` now notify too — a card finished by a rule still reaches the customer). Milestone columns are keyed off **status id** (same deal as `RECEIVED_STATUS_ID`): 1 รอรับเรื่อง + no assignee → `needs_assignment` to every admin (+ reporter); 2 รอดำเนินการ → `status_pending`; 3 กำลังดำเนินการ → `in_progress`; 4 เสร็จสิ้น → `completed` (+ every admin); **every other column → plain `moved` to assignee + reporter only** — routine drags no longer flood the admin inbox. Assignment: `assigned` → new assignee + reporter; clearing it → `unassigned` → the person who lost the card + every admin. `created` still fans out to every admin (`alsoAdmins: true`), `commented` fans out only while the card has **no** assignee, and `RulesService.create/update/toggle/remove` notify admins with `rule_created` / `rule_updated` / `rule_deleted` (link `/automation/{id}`). All fan-outs skip the actor and stay best-effort.
- **Roles are `"admin" | "programmer" | "customer"`** (3 roles, stored in the `roles` table — not an enum). Renamed from `"user"` → `"customer"` (done); see `design.md` §8.
- **`permissions` table** (queried via raw SQL, not a TypeORM entity): columns `id`, `code`, `action`, `category`. `role_permissions` table: TypeORM entity with uuid `id`, `role`, `permission`.
- **`Position` entity**: `id` (int), `name` (unique), nullable `role_id` → `Role`, and a `position_permissions` relation. `User` has a nullable `position` column. Effective perms = role perms ∪ position perms; `PermissionsService.hasPermission(roleId, permission, positionId?)` checks both, and JWT carries `positionId`.
- **Assignment is manual — category auto-assign is parked.** `IssuesService.create()` no longer resolves an assignee from `categories.position` (`resolveAutoAssign()` and the `Position` repository injection were removed), so a new card starts with `programmerId = null` and an admin assigns it on the board through `PUT /issues/:id/assign` (which writes the `card.assigned` activity row and notifies the assignee). `categories.position` is **legacy**: the column still holds its data (`Frontend` / `Backend`) and `PATCH /categories` still accepts it, but nothing reads it at runtime — dropping the column waits for the senior's go-ahead.
- **ไทย:** `JwtAuthGuard` เป็น global guard ผ่าน `APP_GUARD`; ยกเว้นด้วย `@Public()`. JWT หมดอายุ 7 วัน ไม่มี refresh flow
- **ไทย:** **ไม่มี auto-seed** — บัญชีมาจาก `apps/api/src/seed.ts` (`npm run seed`) ซึ่งจะสร้าง `admin@example.com` แต่บัญชีนี้**ไม่มีอยู่จริง**ใน DB จริง; บัญชีจริงคือ `aom@gmail.com` (admin, id 1), `arthitaya@gmail.com` (id 2), `programmer@gmail.com` (id 13), `b@gmail.com` รหัส `123456` ทุกบัญชี
- **ไทย:** `User.id` เป็น integer คอลัมน์ `password` map ไป `passwordHash`; `RolePermission.id` เป็น uuid (PK ปนกัน). `synchronize: false` เสมอ — เปลี่ยน schema ต้องผ่าน migration (ดูกฎคำสั่งด้านบนว่าตัวไหน track อะไร)
- **ไทย:** สิทธิ์ระบบอัตโนมัติคือ `automation.view` / `automation.update` (migration 0031) — `RulesController` และหน้า `/automation` ทั้ง 4 อ้างอิงตัวนี้
- **ไทย:** **ตาข่ายการลาก — ย้ายทีละคอลัมน์**: เมื่อมี rule ที่ active ด้วย action `issue.move_step_only` (trigger `issue.moved`, template `moved_any`) → `IssuesService.move()` จะโยน **400 ก่อนเขียนข้อมูล** ถ้าลากข้ามคอลัมน์ (ความ "ติดกัน" = ลำดับใน `issue_statuses.position` ตามที่บอร์ดเรียง; การ์ดที่ยังไม่มีสถานะและกรณีอ่านลำดับไม่ได้จะผ่าน — fail open). ธงเดียวคือ `RulesEngineService.isStepOnlyMoveActive()` และ `case "issue.move_step_only":` ใน `runAction` **ต้องคงไว้** (test registry บังคับว่า action ที่ supported ต้องมี case) ซึ่งคืน *skipped* เพราะ engine ยังถูกเรียกหลังย้ายจริง. `GET /issues/move-policy` คืน `{ stepOnly }` ให้บอร์ดงด preview (key i18n `Boards.invalidTransition` + fallback จับ 400 ใน `handleDragEnd`) — **seed เปิดไว้** โดย migration `1801000000000` (กฎ "บังคับลากการ์ดทีละคอลัมน์") pause ใน `/automation` เพื่อกลับไปลากอิสระ; เงื่อนไขของ action นี้ถูก**ไม่สนใจโดยเจตตานะ** เพื่อให้ flag ฝั่งบอร์ดกับฝั่งเซิร์ฟเวอร์ตรงกัน และ action `issue.move_status` เขียนข้อมูลตรง ๆ จึงยังข้ามได้ตามเดิม
- **ไทย:** **ล็อกสถานะ — "การ์ดในสถานะนี้ลากออกไม่ได้"**: rule ที่ active ด้วย action `issue.lock` **พร้อมระบุสถานะ** (เงื่อนไข `to_status` เช่น template `moved_to`) จะแช่แข็งการ์ดทุกใบในสถานะนั้น — คำนวณ **ตอนอ่าน/ตอนย้าย** จาก `RulesEngineService.statusGates(...).locked` ดังนั้นการ์ดที่นั่งอยู่ก่อนแล้วจะถูกล็อกทันทีที่เปิดกฎ และ pause กฎเมื่อไหร่ก็ปลดทันที; `case "issue.lock":` ใน `runAction` ของกฎแบบนี้จึง**ไม่เขียน flag รายใบ** (คืนเหตุผล "status lock is enforced at read time") เฉพาะ rule `issue.lock` **ที่ไม่มีเงื่อนไข** เท่านั้นที่ยังเขียน `issues.is_locked` ตอน trigger fire (ล็อกใบเดียว เช่น "created → lock"). `IssuesService.move()` โยน **409 Conflict ก่อนเขียน** ถ้าสถานะของการ์ดถูกล็อกหรือ `is_locked` ตั้งอยู่ (บอร์ดแสดง `Boards.lockedCard`; ตัวลากถูกปิดฝั่ง client อยู่แล้วผ่าน `issue.isLocked` ดังนั้น 409 เป็นตาข่ายสำหรับ state ที่เก่า — ใช้ 409 ไม่ใช่ 400 เพื่อแยกจาก guard ย้ายทีละคอลัมน์). **ปลดล็อกครั้งเดียว**: `PUT /issues/:id/unlock` (perm `issue.all.update`) ล้าง `is_locked` และตั้ง `lock_exempted` (migration `1802000000000`) — การย้ายสำเร็จครั้งต่อไปจะบริโภคมัน (`lock_exempted: false` ในการเขียนเดียวกัน) จึงล็อกใหม่เมื่อเข้าสถานะล็อกอีก. บอร์ดจะแสดงปุ่มปลดล็อก (เมนู "..." ของการ์ด + ไอคอนกุญแจขอบล่าง) **ก็ต่อเมื่อมี rule `issue.unlock` active อย่างน้อย 1 อัน** — `GET /issues/move-policy` → `{ stepOnly, unlockAvailable }` (fail-closed ถ้า lookup พัง); ไม่มีกฎปลดล็อก = สถานะถูกผนึก ต้อง pause กฎล็อกใน `/automation` เอง. `toResponse()` ส่ง `isLocked` = flag รายใบ OR เกตสถานะ หัก `lock_exempted` ที่ค้างอยู่. ส่วน action `issue.unlock` (ที่ trigger.fire) ทำงานเหมือน endpoint: `{ isLocked: false, lockExempted: true }`

2 รอดำเนินการ → `status_pending`; 3 กำลังดำเนินการ → `in_progress`; 4 เสร็จสิ้น → `completed` (+ แอดมินทุกคน); **คอลัมน์อื่นทั้งหมด → `moved` ธรรมดาให้แค่ผู้รับ + ผู้แจ้ง** — การลากทั่วไปไม่ còn spam กล่องแอดมิน. การมอบหมาย: `assigned` → ผู้รับใหม่ + ผู้แจ้ง; ## Authorization (implemented — extend, don't reinvent) / สิทธิ์การเข้าถึง

- Permission-driven authz **already exists**: `@Permissions(...)` decorator + `RolesGuard` in `apps/api/src/modules/auth/`. Permissions live in `packages/shared/src/permissions.ts`.
- `@Permissions()` alone does **nothing**. You must also apply `@UseGuards(RolesGuard)` (per route or controller).
- Runtime checks query the DB through `PermissionsService` (`role_permissions` table), **not** `ROLE_PERMISSIONS`. `ROLE_PERMISSIONS` / `roleHasPermission` are only the seed + the frontend mirror (`apps/web/src/lib/permissions.ts`, `usePermissions().can`), so they can drift after an admin edits the matrix.
- `hasPermission` short-circuits: always returns `true` for `admin`.
- **ไทย:** ต้องใส่ `@UseGuards(RolesGuard)` ด้วย ไม่งั้น `@Permissions()` ไม่มีผล
- **ไทย:** ตอนตรวจสิทธิ์จริงอ่านจาก DB ผ่าน `PermissionsService` ไม่ใช่ `ROLE_PERMISSIONS`
- **ไทย:** `hasPermission` คืน `true` เสมอสำหรับ `admin`
